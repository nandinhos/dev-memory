# 🟢 ONDA 1 — HO-2026-08-22-001 · Operar como dono

**Objetivo único:** o DSH passa a operar o hub com visão administrativa (110 memórias, 17 projetos, perfis de harness) e o repo fica higienizado.
**Tipo:** operação pura — **zero mudança de código**.

## Escopo
- ✅ Emitir token global de admin; religar `DEV_MEMORY_API_KEY` no DSH.
- ✅ Ativar HSTS (Cloudflare edge).
- ✅ Remover `cookies.txt` do repo e gitignorar.
- ❌ Não criar perfis de harness (Onda 2). Não instalar hooks (Onda 3).

## Bloqueios
- 🔒 **A UI `/admin/tokens` não cria token global** (verificado em `ApiTokens.php`). Único caminho: `tinker` no servidor.
- 🔒 Exige `User::is_admin = true` (confirmar antes).
- 🔒 Reiniciar a sessão/processo do DSH para recarregar a env var.

## Passos (comandos exatos)
1. **Pré-check (local):** `curl -s https://devmemory.fssdev.com.br/up` → 200; `git status -sb` na máquina local (dev está ahead 3 de origin/dev — registrar, não resolver aqui).
2. **SSH na VPS:** `cd /var/www/devmemory.fssdev.com.br/current`.
3. **Confirmar admin:**
   ```php
   php artisan tinker
   > App\Models\User::where('is_admin', true)->pluck('email');
   ```
4. **Emitir token global (interativo, copiar o plaintext direto para o destino — sem chat):**
   ```php
   > $u = App\Models\User::where('is_admin', true)->first();
   > [$t, $plain] = App\Models\ApiToken::issue($u, 'dsh-global', null, null, true);
   > echo $plain;
   ```
5. **Atualizar o DSH:** `~/.dsh/.env` → `DEV_MEMORY_API_KEY=<plaintext>` (via editor local).
6. **Reiniciar sessão do DSH** (novo processo lê o `.env`).
7. **Revogar o token antigo** (project-bound) em `/admin/tokens` **depois** de validar o novo (passo 8).
8. **HSTS:** Cloudflare → SSL/TLS → Edge Certificates → HSTS on (max-age 31536000, includeSubdomains).
9. **Higiene repo:** `git rm --cached cookies.txt` + adicionar `cookies.txt` ao `.gitignore` → commit → push (branch dev; merge via PR quando conveniente).

## Critérios de aceite (verificar por output)
- [ ] `mcp__dev-memory__memory_stats` → `total` = **110+** (antes: 12).
- [ ] `mcp__dev-memory__harness_list` → responde (estado real do hub, mesmo que vazio).
- [ ] `curl -sI https://devmemory.fssdev.com.br/ | grep -i strict-transport-security` → presente.
- [ ] `git status` → sem `cookies.txt` untracked.

## Rollback
- Revogar o token novo em `/admin/tokens`; restaurar `DEV_MEMORY_API_KEY` antigo; desativar HSTS; restaurar `cookies.txt` via `git restore --source`.

## Handoff para a Onda 2
- Estado: DSH admin ativo; token global **válido e vigente** (o plaintext fica só em `~/.dsh/.env`).
- Aviso: **não rotacionar este token antes da Onda 8**.

# 🟢 ONDA 2 — HO-2026-08-22-002 · Prova do ciclo de harness

**Objetivo único:** provar ponta a ponta que o hub reconstrói o ambiente (captura sanitizada → provision → máquina limpa) — a promessa central do segundo cérebro.
**Tipo:** operação via MCP + máquina de teste.

## Escopo
- ✅ Capturar o perfil `claude-code` do ambiente atual via MCP.
- ✅ Gerar plano de provision + instalador.
- ✅ Aplicar numa **máquina de teste limpa** (WSL/container descartável) e validar idempotência.
- ❌ Não expandir para Codex/Antigravity/Hermes nesta onda (fica como extensão pós-validação).

## Bloqueios
- 🔒 Onda 1 concluída (token global enxerga perfis).
- 🔒 Máquina de teste disponível (sem config real do usuário).
- 🔒 `jq` não é necessário aqui (só na Onda 3).

## Passos
1. Na máquina de origem: `mcp__dev-memory__harness_paths(harness: "claude-code")` → anotar os paths que existem.
2. Ler os arquivos existentes (ex.: `~/.claude/CLAUDE.md`, `~/.claude/settings.json`, `.mcp.json` do projeto) e montar `files: [{path, content}]`.
3. `mcp__dev-memory__harness_capture(harness: "claude-code", files: [...], name: "default")` → conferir resposta: `files_stored`, `files_with_redactions` (segredos redigidos).
4. `mcp__dev-memory__harness_list` → perfil presente com `version` e `files` contados.
5. `mcp__dev-memory__harness_provision(harness: "claude-code")` → revisar `steps` + `notes` (flag `had_secrets`).
6. `mcp__dev-memory__harness_installer_script(harness: "claude-code")` → salvar `install.sh`.
7. Na máquina limpa: `bash install.sh` (interativo). Rodar **2ª vez** sem `--force` → deve **abortar** (idempotência).
8. Validar: `~/.claude/CLAUDE.md` e `.mcp.json` presentes; `php artisan mcp:serve` (ou equivalente) responde `tools/list` local.

## Critérios de aceite
- [ ] `harness_capture` retorna `files_with_redactions` listando quais arquivos tiveram segredos.
- [ ] 2ª execução do instalador na máquina limpa **aborta** (não sobrescreve) sem `--force`.
- [ ] `.mcp.json` provisionado aponta para o hub (bootstrap recursivo).
- [ ] Nenhum segredo real aparece no conteúdo armazenado (conferir via `harness_provision`).

## Rollback
- Remover perfil via `/admin/harness` (UI) ou `HarnessProfile::where(...)->delete()`.
- Na máquina de teste: apagar arquivos provisionados (é descartável).

## Handoff para a Onda 3
- Perfil `claude-code` v1.x capturado e **validado em máquina real**.
- Decisão registrada: qual harness é o alvo do primeiro hook (recomendado: `claude-code`).

## Critérios de aceite

- [ ] O hook **não bloqueia** o harness (roda em background — `&` no script).
- [ ] Mesmo conteúdo enviado 2× → `deduplicated: true` (idempotência).

## Rollback

## Handoff para a Onda 4
